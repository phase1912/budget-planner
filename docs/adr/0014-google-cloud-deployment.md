# ADR 0014: Production runs on Google Cloud at the smallest sizes that work

**Date:** 2026-10-08
**Status:** Accepted — supersedes [ADR-0002](0002-cloud-provider-aws.md)

## Context

ADR-0002 chose AWS before any infrastructure existed; the AWS account it assumed is
closing and nothing was ever provisioned there. The project now has a Google Cloud
account with $300 of trial credit until early December and about $10 a month of
standing credit after that. The only real user until the diploma defence is the author,
so the goal is the cheapest deployment that runs the product reliably, can be scaled
later without redesign, and deploys itself on every merge.

Measured on the local stack (2026-10-08): the backend idles at 139 MB, the database
holds 9 MB, a receipt's photos average 4.6 MB, the frontend is static files.

## Decision

One environment, **production**, in `us-central1` (the free tiers below apply only in
US regions; ~120 ms from Poland is unnoticeable here). Staging is not built.

| Part | Choice | Why |
|---|---|---|
| Backend | **Cloud Run** service, 1 vCPU / 1 GiB, 0 to 2 instances, CPU always allocated | Runs the existing image, scales to zero, free tier covers one user. CPU must stay allocated after a response: receipts are read in background tasks. 1 GiB leaves headroom for converting large HEIC photos. |
| Migrations | Cloud Run **job** on the same image, `alembic upgrade head`, run by each deploy before the service updates | Migrations never run inside a serving instance. |
| Database | **Postgres 16 on an e2-micro VM** (Container-Optimized OS), data on its own persistent disk, daily snapshots kept 7 days, reachable only inside the VPC | The free-tier VM costs nothing; Cloud SQL's smallest tier is ~$10 a month for the same job. Everything about it is in Terraform, so nothing is configured by hand. |
| Photos | **Cloud Storage**, natively, as the backend's service account (`STORAGE_BACKEND=gcs`, `app/adapters/gcs_storage.py`) | 5 GB is free. The S3 interoperability API was the first choice — the aiobotocore adapter would have worked unchanged — but it needs an HMAC key, and the organisation's default policy `iam.disableServiceAccountKeyCreation` forbids every service account key. Presigned URLs are signed by IAM (`signBlob`), so no key exists anywhere. Locally MinIO stays behind the S3 adapter. |
| Frontend | **Firebase Hosting** | Free static hosting with HTTPS and a CDN; the app calls the Cloud Run URL directly (bearer tokens, CORS allow-list). |
| LLM | **Vertex AI Gemini** through LiteLLM (`vertex_ai/gemini-2.5-flash`) | The service account authenticates, so there is no API key to manage, and paid-tier requests are not used to train Google's models (BRD N1). |
| Inbound mail | **App Engine** relay (ADR-0013) | The one Google Cloud path that receives mail without a paid domain. |
| Secrets | **Secret Manager**, mounted as environment variables | JWT key, database URL, inbound mail secret; generated by Terraform, never in git. |
| CI access | **Workload Identity Federation** for GitHub Actions | No long-lived JSON key exists to leak. |
| Infrastructure | **Terraform**, one root module in `infra/terraform/`, state in a GCS bucket | Files split by concern; no modules until a second environment exists. |
| Cost guard | **Billing budget** with alerts at $5, $10 and $20 | The expected bill is $1–4 a month; an alert means something is wrong. |

Deploys run from GitHub Actions after CI passes on `main`: build and push the image,
run the migrations job, deploy the service, publish the frontend, redeploy the mail
relay when it changed, and check `/health`. `terraform apply` stays a deliberate local
step; CI only formats and validates the Terraform.

## Consequences

- **The database is ours to run.** Postgres version upgrades, disk growth and restores
  are manual; the runbook in `infra/terraform/README.md` covers restoring from a snapshot.
  Moving to Cloud SQL later is a Terraform change plus a dump and restore.
- **Cold starts.** After 15 idle minutes the backend scales to zero; the next request
  waits about 5–10 s. Wake it before a demonstration.
- **The proactive advice pass (F8.8) runs only while an instance is up**, because it is
  scheduled in-process. A Cloud Scheduler trigger is the fix if that ever matters.
- **Migrations run before the new code, against the old code.** Each deploy runs
  `alembic upgrade head` as the `migrate` job and deploys the service only if it succeeds,
  so a failed migration leaves the previous version serving. Between the two steps the old
  revision runs on the new schema, so a migration must stay compatible with the code
  before it: add first, remove later. Dropping or renaming a column the running code still
  reads takes two merges — the code stops using it, then a migration removes it. Alembic
  downgrades are never run by the pipeline; a bad migration is fixed forward.
- **No staging.** A defect reaches production on merge; CI is the only gate. Adding
  staging later means a second `.tfvars` and the modules this ADR deliberately defers.
- **Lock-in is shallow.** The application sees Postgres, an S3 API, environment
  variables and a container — the AWS and Azure estimates from 2026-10-08 remain valid
  alternatives behind the same seams.
